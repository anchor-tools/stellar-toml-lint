# tree-sitter-stellar-toml

A [tree-sitter](https://tree-sitter.github.io/tree-sitter/) grammar for
`stellar.toml` (SEP-1). It is a TOML 1.0 grammar plus five concrete nodes for
the structures an anchor file is made of, so that editors and symbol indexes can
name a Stellar public key instead of pattern-matching one out of a string.

| Node             | Matches                                                                             | Example                                                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `public_key`     | a quoted ed25519 account (`G`, 56 characters) or muxed account (`M`, 69 characters) | `"GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5"`, `"MCGZSP4K4SG7CU2L2ANFGFY7XQLK2LD333DBYE6TYL7FQPAAZ4QE4ABAAAAAAAAAAG6X2"` |
| `contract_id`    | a quoted Soroban contract id (`C`, 56 characters)                                   | `"CA32UWEBA6HNQTOHALV2LAX6DMUQFSRL7XH4U7QFBPRKE5KPWJU7LWKS"`                                                                            |
| `asset_code`     | a quoted 1–12 character alphanumeric asset code                                     | `"USDC"`                                                                                                                                |
| `sep_table`      | a reserved SEP-1 table header                                                       | `[DOCUMENTATION]`, `[VALIDATORS]`                                                                                                       |
| `currency_entry` | a `[[CURRENCIES]]` array-of-table header                                            | `[[CURRENCIES]]`                                                                                                                        |

Grammar name `stellar_toml`, scope `source.stellar-toml`, file type `toml`.

## What the grammar deliberately does not do

The three scalar nodes match a **shape**, not a validity. `public_key` will
happily wrap a key whose CRC16 checksum is wrong, because an editor still wants
to highlight and index it, and a rejected token would silently degrade the whole
line back to a plain string. Checksum validity belongs to the linter —
see `isAccountId`, `isContractId` and `isMuxedAccountId` in `src/predicates.ts`.
The same division is why `sep_table` and `currency_entry` are lexed by the
external scanner rather than by token rules: a token rule for `DOCUMENTATION`
would also win inside `[DOCUMENTATIONX]`, because token precedence outranks
match length in the lexer.

Vendor extensions (any key or table SEP-1 does not define) still parse: a value
that does not fit one of the shapes above is an ordinary `string`, and a key that
is not a reserved header is an ordinary `bare_key`.

## Layout

```text
grammar.js                    the grammar (the source of truth for the language)
src/                          generated by `tree-sitter generate` — commit it, never edit it
bindings/node/                Node binding
bindings/wasm/binding.c       WASM entry point (`tree_sitter_stellar_toml`)
queries/highlights.scm        syntax highlighting
queries/folds.scm             fold regions
queries/tags.scm              symbol index (definitions and references)
test/corpus/*.txt             parse expectations, replayed by `tree-sitter test`
```

`src/` is checked in so that consumers without the CLI (Helix's
`hx --grammar build`, a distro packager) can compile the parser from C alone.
It must always be regenerated in the same commit as `grammar.js`;
`test/tree-sitter-grammar.test.ts` fails if the two drift apart.

## Regenerating and testing

```sh
cd grammars/tree-sitter-stellar-toml
tree-sitter generate   # rewrites src/
tree-sitter test       # replays test/corpus/*.txt
```

From the repository root, the same three steps run as one command, and also try
a WASM build when a toolchain is reachable:

```sh
TREE_SITTER_CLI="$HOME/.cargo/bin/tree-sitter" node scripts/build-tree-sitter-grammar.mjs
```

The CLI is **looked up, never installed**. `tree-sitter-cli` is an npm package
with a postinstall that downloads a native binary, which the
"Malware and supply-chain check" CI job rejects, so no lockfile in this
repository refers to it. Without a CLI the script prints what is missing and
exits 0; the CLI-free half of the invariants is enforced by
`test/tree-sitter-grammar.test.ts`, which runs in the normal `npm test` suite.

To re-record corpus expectations after an intentional grammar change:
`tree-sitter test -u`, then read the diff before committing it.

## Neovim

Neovim 0.10 and newer have tree-sitter built in, so no plugin is required. Build
the parser into your runtime directory and copy the queries beside it:

```sh
cd grammars/tree-sitter-stellar-toml
tree-sitter generate
mkdir -p "$HOME/.local/share/nvim/site/parser" "$HOME/.local/share/nvim/site/queries/stellar_toml"
tree-sitter build -o "$HOME/.local/share/nvim/site/parser/stellar_toml.so"
cp queries/highlights.scm queries/folds.scm "$HOME/.local/share/nvim/site/queries/stellar_toml/"
```

Neovim searches the `parser/` runtime directory for `{lang}.*` and loads
`queries/{lang}/{highlights,folds}.scm` by the same name, which is why the
directory is `stellar_toml` and not `stellar-toml`. Then attach the parser to
anchor files only, so ordinary TOML keeps its own parser:

```lua
-- ~/.config/nvim/init.lua
vim.api.nvim_create_autocmd({ 'BufNewFile', 'BufRead' }, {
  pattern = 'stellar.toml',
  callback = function(ev)
    if vim.treesitter.language.add('stellar_toml') then
      vim.treesitter.start(ev.buf, 'stellar_toml')
    end
  end,
})
```

`vim.treesitter.language.add()` returns false when the parser is not installed,
so the block above is safe on a machine that has not run the build. If you would
rather have every `.toml` buffer parsed by this grammar, use
`vim.treesitter.language.register('stellar_toml', 'toml')` instead of the
autocommand. The captures in `queries/highlights.scm` are all names Neovim links
to its standard highlight groups; an unrecognised capture is dropped without a
warning, which is why the `; Captures:` header in each query file lists exactly
the set the file uses, and why a test enforces that.

## Helix

Helix compiles grammars named in your `languages.toml`, so no fork of Helix is
needed:

```toml
# ~/.config/helix/languages.toml
[[grammar]]
name = "stellar-toml"
source = { git = "https://github.com/anchor-tools/stellar-toml-lint",
           rev = "<a commit or tag containing this directory>",
           subpath = "grammars/tree-sitter-stellar-toml" }

[[language]]
name = "stellar-toml"
scope = "source.stellar-toml"
injection-regex = "stellar-toml"
file-types = [{ glob = "stellar.toml" }]
comment-tokens = "#"
```

```sh
hx --grammar fetch && hx --grammar build
```

`subpath` is required because this repository hosts the grammar in a
subdirectory; `rev` must be a commit hash or a tag, not a branch. Fetch a
grammar from a local checkout while developing by replacing `source` with
`{ path = "/absolute/path/to/stellar-toml-lint/grammars/tree-sitter-stellar-toml" }`
— Helix builds `src/parser.c` and `src/scanner.c` from that directory, so
`tree-sitter generate` has to have run there first.

Helix loads queries for a language from `runtime/queries/<language-name>/`, and
the user config directory is on that search path:

```sh
mkdir -p "$HOME/.config/helix/runtime/queries/stellar-toml"
cp queries/highlights.scm queries/folds.scm queries/tags.scm \
   "$HOME/.config/helix/runtime/queries/stellar-toml/"
```

`tags.scm` is what feeds Helix's document and workspace symbol pickers; Neovim
reads highlights and folds and leaves `tags.scm` to `tree-sitter tags`. Use a
`glob` rather than `file-types = ["toml"]` unless you want the grammar for every
TOML file in your editor. If Helix reports the language but cannot find the
queries, set `HELIX_RUNTIME` to the `runtime` directory you are developing in.
A stale or broken compiled parser is the file `hx` loads as
`runtime/grammars/stellar-toml.so`; delete it and rebuild.

## WASM binding

`bindings/wasm/binding.c` exposes the standard entry point
`tree_sitter_stellar_toml`, and the build script puts the module in
`dist/wasm/`, which is gitignored: this repository ships the grammar as source,
never as a compiled binary. Building it needs emscripten (`emcc`) or a running
Docker daemon, otherwise step 3 is skipped with an explanation;
`TREE_SITTER_SKIP_WASM=1` skips it on purpose, and
`TREE_SITTER_ALLOW_WASI_SDK=1` lets the CLI download its own ~180 MB wasi-sdk
toolchain instead.

```js
import { Parser, Language } from 'web-tree-sitter';

await Parser.init();
const parser = new Parser();
parser.setLanguage(await Language.load('/dist/wasm/tree-sitter-stellar_toml.wasm'));
const tree = parser.parse(await fetch('/.well-known/stellar.toml').then((r) => r.text()));
```

On "zero memory leaks": the external scanner allocates nothing. Its `create`
returns `NULL` and its `serialize` returns 0, which the test asserts, so each
parse frees exactly what the tree-sitter runtime allocated for the tree. A
measured check — `tree-sitter parse` over the 300-line production fixture,
three times — holds RSS flat at ~43.8 MB, i.e. there is no per-parse growth to
find.
